AI and digital inaccessibility

AI is making the web less accessible, and it's happening faster than before. Here's why.


Most code on the internet is already broken for people who use screen readers, keyboards, or voice navigation. According to WebAIM, around 96% of home pages have accessibility failures. That's the web AI learned from. So when you ask an AI to build a website, it copies patterns that were already inaccessible. It doesn't know they're wrong. It just knows they look familiar.

And here's the thing: when people ask AI to create a website, they say "make me a portfolio with a hero section, a project gallery, and a contact form." They don't say "make it accessible" or "follow WCAG 2.1" or "comply with the ADA." Why would they? Most people don't think about it. The visual result is what matters to them. So the AI optimizes for what was asked. Accessibility never enters the prompt, so it never enters the output.

Even when you do ask, the results are often absurd. Ask for an "accessible button" and you might get a <div> with a click handler, styled to look clickable but invisible to assistive technology. Ask for a modal and you get something that looks right in a screenshot but traps keyboard users with no escape. Tell it to add ARIA and it sprinkles labels on random elements like it's decoration. The AI learned what interfaces look like. It didn't learn how they work for people who don't use a mouse.

These aren't edge cases. They're the default output. A 2025 ACM study found that LLMs can produce valid HTML but "frequently fail to meet full accessibility compliance without further prompting and human interventions." Even when prompted specifically for accessibility, improvements are partial. Alt text and status management stay broken.

And better prompts only go so far. Researchers compared accessibility-focused prompts against regular ones. The focused prompts did improve compliance, but didn't eliminate failures. Accessibility isn't a feature you bolt on with a sentence. It's a property of correct implementation: focus flows logically, semantics match behavior, state changes get announced, and everything responds to keyboards and screen readers. AI trained on visual patterns can't reliably infer that.

So what happens when this code ships? Real people hit real barriers. A screen reader user can't complete a purchase because a dropdown has no accessible name. A keyboard user gets trapped in a modal with no way out. Someone using voice navigation can't activate a "button" that's actually a div. A person with a cognitive disability can't parse form errors that were never programmatically connected to their fields. These aren't hypothetical. They're predictable.

The good news is that the same AI tools can be pointed at the problem. Several MCP servers and agent skills now let AI audit its own output before shipping:

wcag-accessibility-mcp

Gives AI agents WCAG analysis and refactoring tools. It supports WCAG 2.0, 2.1, and 2.2, audits live URLs or raw HTML, and suggests fixes. github.com/alexanderuk82/mcp-wcag-accessibility

@accesslint/mcp

Built for accessible agentic coding. It audits HTML, files, and URLs, and includes a diff tool to verify fixes against a baseline. In benchmarks, agents using it fixed 99.5% of violations, versus 93.5% working alone. github.com/AccessLint/mcp

@a11yeco/mcp

Runs entirely offline with zero telemetry. It scans localhost servers, evaluates HTML in memory before it's written to disk, and catches regressions against baselines. npmjs.com/package/@a11yeco/mcp

a11y-agent-skills (smukh)

Encodes accessibility expertise for specific UI patterns like comboboxes and autocomplete. Instead of auditing after the fact, it guides generation toward correct patterns from the start. github.com/smukh/a11y-agent-skills

a11y-agent-kit (mfairchild365)

Includes a skill for building accessible UI and a read-only reviewer agent that audits code, runs axe-core, checks the rendered UI in a real browser, and produces a prioritized fix list without touching your code. github.com/mfairchild365/a11y-agent-kit

These tools won't catch everything. Keyboard interaction logic, screen reader announcement order, and zoom behavior still need human testing. But they catch the common machine-detectable failures before they ship. And they give AI the feedback loop it currently lacks.

The accessibility of the AI-generated web won't be decided by the AI. It'll be decided by whether the people using it ask for accessibility, check the output, and install the tools that make checking possible. The tools exist. The prompts can include it. The question is whether anyone bothers.
